# LocalOps desktop frontend

The frontend (`cmd/desktop/frontend`) is a React/TypeScript/Vite application
treated as production code, not a prototype. This document is the reference
for how it's organized and how to work in it — for contributors and for
future AI-assisted work alike.

## Stack

- **React 18** + **TypeScript** + **Vite**
- **TanStack Router** — file-based routing (`src/routes/`), typed navigation
- **TanStack Query** — the only layer that talks to Wails-backed async state
- **Tailwind CSS v4** (`@tailwindcss/vite`) — styling, backed by LocalOps's own design tokens
- **Vitest** + **React Testing Library** — tests
- **ESLint** (flat config) + **Prettier** (`prettier-plugin-tailwindcss`) — lint/format
- `@wailsio/runtime` + generated Wails bindings (`bindings/`, gitignored, regenerated by `wails3`)

## Folder responsibilities

```text
src/
├── app/            Global setup: providers (QueryClientProvider), the
│                   router instance, global styles, and the app shell
│                   (Sidebar/AppShell) — the chrome every route renders inside.
├── routes/         TanStack Router file-based routes. Thin: each route
│                   file validates its own params/search and renders a
│                   feature component. Never put real logic here.
├── features/       User-facing actions/use cases: add-project, the
│                   Projects dashboard composition, Project Detail's
│                   composition + its section tabs. Feature-local
│                   model/ui/api as needed.
├── entities/       Domain presentation + data: project/ (the Wails API
│                   boundary, query keys/hooks, and the entity's own UI
│                   like ProjectRow/HealthBadge).
└── shared/         Framework-agnostic reusable code with no product
    ├── ui/         knowledge: shared/ui uses Atomic Design (atoms = small
    │   ├── atoms/  primitives like Button/Badge/StatusBadge/MonoText;
    │   └── molecules/ molecules = small compositions like EmptyState/SectionHeader).
    ├── lib/        Atomic Design applies ONLY to this shared layer — feature-
    └── ...         specific components stay in features/entities, never
                     forced into "atoms/molecules/organisms" terminology.
```

Don't create a directory (or an empty `shared/hooks`/`shared/types`) before
something real needs to live there.

## Routing

Two routes today:

- `/` — Projects dashboard (`routes/index.tsx` → `features/projects/ProjectsPage`).
- `/project` — Project Detail (`routes/project.tsx` → `features/project-detail/ProjectDetailPage`).

**A registered project's identity is an absolute filesystem path.** It is
never encoded as a URL path segment (illegal characters, and it would leak
local filesystem layout into something that looks like a routable URL).
Instead `/project` carries `path` and `tab` as a typed **search parameter**,
validated through TanStack Router's own `validateSearch` — no Zod needed for
a shape this small. Project Detail's active tab lives in this search param
too, so it survives navigation history rather than being pure local state.

The route tree (`src/routeTree.gen.ts`) is generated by
`@tanstack/router-plugin`'s Vite plugin on every `pnpm dev`/`pnpm build`
(with automatic code splitting enabled) and regenerated/updated automatically
whenever a route file changes. Per TanStack Router's current recommendation,
**it is committed to source control** — it's generated code, but it's part
of the app's runtime/source contract, and a fresh checkout + `pnpm install`
should not require a build just to make `pnpm typecheck`/`pnpm lint`/
`pnpm test:run` work. Never hand-edit it; it's excluded from ESLint and
Prettier.

## Wails API boundary and Query

`entities/project/api/projectApi.ts` is the **only** module that imports the
generated Wails `Service` binding. Everything else — query/mutation hooks,
components — goes through it. This keeps imports honest and gives tests one
small seam to mock instead of requiring a real Wails process.

`entities/project/model/queries.ts` centralizes query keys (`projectKeys`)
and the query/mutation hooks built on `projectApi`:

- `useProjectsOverviewQuery()` — `["projects", "overview"]`
- `useProjectDetailQuery(path)` — `["projects", "detail", path]`
- `useInvalidateProjectsOverview()` — used after a mutation that changes the registry

`features/add-project/model/useAddProjectMutation.ts` is a `useMutation` that
opens the native picker, registers the result, and invalidates the Projects
overview query on success — no manual `useState`-based server-state sync.

Never write a raw query-key array in a component. Add a hook to the relevant
entity/feature `model/` instead.

Local, ephemeral UI state (e.g. a dismissed inline error) still uses plain
React state — TanStack Query is only for state that actually came from Wails.

## Styling

Tailwind v4, configured entirely in CSS (`app/styles/index.css` +
`app/styles/tokens.css`) — no `tailwind.config.js`. LocalOps's existing
design tokens (`--bg`, `--surface`, `--accent`, `--success`, etc.) are plain
CSS custom properties in `tokens.css`, flipped under
`prefers-color-scheme: light` exactly as before. `index.css`'s `@theme`
block maps Tailwind color/radius/font utilities (`bg-surface`,
`text-text-primary`, `rounded-md`, …) onto those same variables, so a
utility class and the token system are always in sync — light/dark support
needed no separate Tailwind configuration.

`shared/lib/cn.ts` (`clsx` + `tailwind-merge`) resolves conditional/
conflicting class lists. Reach for a `shared/ui` primitive instead of
repeating a long className string across features.

## Testing philosophy

Testing Library: test what a user can see/do, not implementation details.
No snapshotting the whole app, no brittle CSS-class assertions.

`shared/lib/test/renderApp.tsx` renders the **real router** (real routes,
real navigation) against an in-memory history and a fresh `QueryClient` —
tests exercise actual routing/query behavior, not a component mounted in
isolation. The only thing tests mock is `entities/project/api/projectApi`
(the Wails boundary) via `vi.mock`; nothing else needs mocking, and no test
requires a real Wails process.

Run with `pnpm test` (watch), `pnpm test:run` (once), `pnpm test:coverage`.

## Lint / format workflow

```bash
pnpm typecheck       # tsc --noEmit
pnpm lint            # eslint . (flat config: typescript-eslint, react-hooks, react-refresh, jsx-a11y)
pnpm lint:fix
pnpm format          # prettier --write . (prettier-plugin-tailwindcss keeps utility order stable)
pnpm format:check
pnpm test:run
pnpm build
```

Or from the repo root: `make check` (never auto-fixes) / `make fmt` (formats
Go and frontend; the only mutating target).

## Import aliases

`@/*` → `src/*`, `@bindings/*` → `bindings/*` (used only by `projectApi.ts`).
Configured once, in `tsconfig.json`'s `paths`; Vite and Vitest both resolve
them via Vite 8's native `resolve.tsconfigPaths` (no `vite-tsconfig-paths`
dependency needed). Never write a deep `../../../` relative import when `@/`
reaches the same file.

## Visual system

LocalOps's visual language is deliberately restrained: a native-feeling,
information-dense desktop tool, not a marketing surface. These conventions
exist so new UI reads as part of the same system rather than a one-off.

- **Typography scale** — five named roles, declared once in
  `app/styles/tokens.css` (`--font-size-*`) and mapped to Tailwind utilities
  in `app/styles/index.css`'s `@theme` block: `text-micro` (11px — section
  labels, counts, auxiliary mono metadata), `text-body` (12.5px — normal
  labels, secondary text, descriptions), `text-emphasis` (13px — row/identity
  text: project names, tool names, nav labels, tabs), `text-title-sm` (15px —
  Project Detail's project title), `text-title` (19px — the Projects page
  title). Reach for the role that matches the text's job, not the pixel
  value closest to what you'd otherwise guess. Do not add a new arbitrary
  `text-[..px]` literal; if none of the five roles fit, that's a sign the
  content needs a different treatment, not a sixth size.
- **Color tokens are semantic, not decorative.** `--bg`/`--surface`/
  `--surface-hover` are surfaces; `--border`/`--border-strong` are borders;
  `--text-primary`/`--secondary`/`--muted` are text; `--success`/`--warning`/
  `--danger`/`--muted-bg` are status fills. A background never borrows a
  border token (or vice versa) merely because the color happens to match.
- **One accent color.** `--accent` is the only accent in the app (active
  nav, focus rings, the active tab's underline). Do not introduce a second
  accent hue for a new feature; reuse the existing semantic status colors
  (`success`/`warning`/`danger`) for state, and the one accent for
  selection/focus.
- **Radius** — three tokens, each with a fixed role: `radius-sm` (badges,
  small controls, code chips), `radius-md` (rows, panels, tables, empty
  states — the default for any bounded container), `radius-lg` (reserved for
  a genuinely larger top-level container, not used by default). When in
  doubt, a new container uses `radius-md`.
- **Density** — the app runs dense and quiet: tight row padding, a 12.5-13px
  working size for most content, borders (not shadows or card elevation) as
  the default way to separate items. Reach for a bordered row/line before
  reaching for a padded card; a "card" treatment is justified only when it
  communicates real elevation (e.g. a grouped stat panel), not as a default
  wrapper.
- **Monospace** (`MonoText`, `--font-mono`) is reserved for paths, tool
  names, versions, and variable names — never for ordinary prose.
- **Interaction philosophy** — this is a tool used dozens of times a day,
  not a page visited once. Motion stays limited to near-instant color/
  background transitions (`transition-colors duration-100`) and a loading
  skeleton; there is no scroll-driven animation, parallax, or decorative
  motion anywhere in the app, and new UI should not introduce any.
